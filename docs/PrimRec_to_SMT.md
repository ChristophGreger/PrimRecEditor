# PrimRec to SMT-LIB Horn Encoding

This document describes how normalized PrimRec programs are translated to
SMT-LIB Horn clauses by `src/primrecLanguage/smt2conversion/primrec.ts`.

The translation starts from a `ParseResult`, applies
`recognizeIdiomsInParseResult(result)`, and then emits a list of SMT-LIB
fragments. Joining those fragments with blank lines gives the final `.smt2`
program.

## 1. Output Shape

The public generator is:

```ts
primRecProgramToHornSmt2Parts(result: ParseResult): string[]
primRecProgramToHornSmt2(result: ParseResult): string
```

Postconditions and complete programs are translated by the same
`smt2conversion` module:

```ts
postconditionProgramToHornSmt2Parts(result: PostconditionParseResult): string[]
postconditionProgramToHornSmt2(result: PostconditionParseResult): string

completeProgramToHornSmt2Parts(result: CompleteParseResult): string[]
completeProgramToHornSmt2(result: CompleteParseResult): string
```

The parts are emitted in this order:

```text
1. (set-logic HORN)
2. Nat helper predicate
3. declare-fun block for all PrimRec functions
4. Horn clauses for each function body
```

The helper predicate is deliberately named `nat`:

```smt2
(define-fun nat ((x Int)) Bool
  (>= x 0))
```

User-defined PrimRec functions are emitted with a leading underscore in SMT-LIB,
so a source function such as `Nat` becomes the relation `_Nat`.

## 2. Relational Function Encoding

PrimRec functions are encoded as relations. A function

```text
f(x1, ..., xn)
```

becomes a relation with one additional result argument:

```smt2
(declare-fun _f (Int ... Int Int) Bool)
```

So:

```text
plus(x, y) = r
```

is represented as:

```smt2
(_plus x y r)
```

All quantified variables in generated rules are constrained to natural numbers:

```smt2
(nat x)
(nat r)
```

The Horn clauses should be read under CHC / least-fixpoint semantics. Under that
semantics, the rules define the least relation generated by the program, which
is the intended tight interpretation for primitive recursive functions.

## 3. Basic Expressions

Every non-`primrec` function body becomes one Horn rule:

```text
body evaluates to r
--------------------------------
f(args..., r)
```

### Projection

PrimRec:

```text
id(x) = x;
```

Horn body:

```smt2
(= r x)
```

### Numeric Constants and zero

PrimRec:

```text
z(x) = zero();
three(x) = 3;
```

Horn bodies:

```smt2
(= r 0)
(= r 3)
```

### Successor

PrimRec:

```text
next(x) = succ(x);
```

Horn body:

```smt2
(= succArg x)
(= r (+ succArg 1))
```

The temporary `succArg` is generated so the same lowering strategy also works
for nested expressions.

## 4. Composition

Composition is handled by introducing temporary result variables for each
argument expression.

PrimRec:

```text
f(x, n) = g(h(x), z(n));
```

Relational meaning:

```text
h(x) = hx
z(n) = zn
g(hx, zn) = r
----------------
f(x, n) = r
```

Generated Horn shape:

```smt2
(assert
  (forall ((x Int) (n Int) (r Int)
           (arg0 Int) (arg0_1 Int)
           (arg1 Int) (arg0_2 Int))
    (=>
      (and
        (nat x)
        (nat n)
        (nat r)
        (nat arg0)
        (nat arg0_1)
        (nat arg1)
        (nat arg0_2)
        (= arg0_1 x)
        (_h arg0_1 arg0)
        (= arg0_2 n)
        (_z arg0_2 arg1)
        (_g arg0 arg1 r))
      (_f x n r))))
```

The exact temporary names are implementation details, but the structure is:

```text
lower each argument expression to a temporary
call the outer relation with those temporaries
derive the surrounding function relation
```

This works for arbitrarily nested composition because the lowering is recursive.

## 5. Generic Primitive Recursion

A validated PrimRec definition has this shape:

```text
f(x1, ..., xk, y) = primrec(base, step);
```

where:

```text
base(x1, ..., xk)
step(x1, ..., xk, y, previous)
```

The generic Horn encoding emits two rules.

### Base Rule

```text
base(x1, ..., xk) = r
----------------------
f(x1, ..., xk, 0) = r
```

SMT-LIB shape:

```smt2
(assert
  (forall ((x1 Int) ... (xk Int) (y Int) (r Int))
    (=>
      (and
        (nat x1)
        ...
        (nat y)
        (nat r)
        (= y 0)
        (_base x1 ... xk r))
      (_f x1 ... xk y r))))
```

### Step Rule

```text
f(x1, ..., xk, previousCounter) = previous
step(x1, ..., xk, previousCounter, previous) = r
counter = previousCounter + 1
-----------------------------------------------------
f(x1, ..., xk, counter) = r
```

SMT-LIB shape:

```smt2
(assert
  (forall ((x1 Int) ... (xk Int)
           (counter Int) (r Int)
           (previousCounter Int) (previous Int))
    (=>
      (and
        (nat x1)
        ...
        (nat counter)
        (nat r)
        (nat previousCounter)
        (nat previous)
        (= counter (+ previousCounter 1))
        (_f x1 ... xk previousCounter previous)
        (_step x1 ... xk previousCounter previous r))
      (_f x1 ... xk counter r))))
```

This is the direct Horn version of primitive recursion.

## 6. Idiom Recognition

Before SMT-LIB generation, the parse result is passed through:

```ts
recognizeIdiomsInParseResult(result)
```

That function annotates some `PrimitiveRecursion` expressions with an `idiom`.
The SMT generator then emits a more efficient closed Horn encoding for those
cases instead of the generic recursive two-rule encoding.

The optimization is structural. If no idiom is recognized, the generator falls
back to the generic primitive recursion rules.

### 6.1 LinearRecurrence

Recognized form:

```text
step(..., previous) = previous + C
```

Closed form:

```text
f(..., y) = base(...) + y * C
```

Generated shape:

```smt2
(assert
  (forall ((x Int) (y Int) (r Int)
           (baseResult Int) (increment Int) ...)
    (=>
      (and
        ...
        (_base x baseResult)
        ; increment expression lowered here
        (= r (+ baseResult (* y increment))))
      (_f x y r))))
```

For canonical addition:

```text
plusBase(x) = x;
plusStep(x, y, previous) = succ(previous);
plus(x, y) = primrec(plusBase, plusStep);
```

the increment is `1`, so the generated relation is equivalent to:

```text
plus(x, y, r) <=> r = x + y
```

For multiplication by repeated addition:

```text
mulBase(x) = zero();
mulStep(x, y, previous) = plus(previous, x);
mul(x, y) = primrec(mulBase, mulStep);
```

the idiom recognizer sees:

```text
previous + x
```

so the closed form is:

```text
mul(x, y) = 0 + y * x
```

The generated Horn rule still references `mulBase` and lowers the increment
expression, so the encoding remains connected to the program definitions.

### 6.2 Predecessor

Recognized form:

```text
step(y, previous) = y
```

Closed behavior:

```text
f(0) = base()
f(y) = y - 1, for y > 0
```

Generated rules:

```text
base case:
  counter = 0 and base(...) = r => f(..., counter, r)

positive case:
  counter > 0 and r = counter - 1 => f(..., counter, r)
```

### 6.3 ConstantAfterFirst

Recognized form:

```text
step(..., y, previous) = E
```

where `E` does not depend on the recursion counter `y` or on `previous`.

Closed behavior:

```text
f(..., 0) = base(...)
f(..., y) = E, for y > 0
```

Generated rules:

```text
base case:
  counter = 0 and base(...) = r => f(..., counter, r)

positive case:
  counter > 0 and E lowers to r => f(..., counter, r)
```

This covers definitions such as `isZero`, where the first value comes from the
base function and every positive input maps to a fixed value.

## 7. Example: Multiplication

Input PrimRec:

```text
plusBase(x) = x;

plusStep(x, y, previous) =
  succ(previous);

plus(x, y) = primrec(plusBase, plusStep);

mulBase(x) =
  zero();

mulStep(x, y, previous) =
  plus(previous, x);

mul(x, y) = primrec(mulBase, mulStep);
```

Important generated facts:

```text
plusBase(x, r) derives r = x
plusStep(x, y, previous, r) derives r = previous + 1
plus(x, y, r) uses LinearRecurrence:
  r = plusBase(x) + y * 1

mulBase(x, r) derives r = 0
mulStep(x, y, previous, r) derives plus(previous, x, r)
mul(x, y, r) uses LinearRecurrence:
  r = mulBase(x) + y * x
```

So both `plus` and `mul` are encoded without recursive Horn unfolding in the
final SMT-LIB when the idiom recognizer succeeds.

## 8. Error Handling

The generator expects a valid `ParseResult` with `program` present.

If parsing or validation failed, `ParseResult.program` is absent and generation
throws:

```text
Cannot generate Horn SMT-LIB for an invalid PrimRec program.
```

This keeps SMT generation downstream of the existing PrimRec validation rules:

```text
arity checks
known functions
no forward references
no general recursion
primrec only as a complete function body
base/step arity compatibility
```

## 9. Current Design Choices

- Every function is declared relationally with one result argument.
- `zero` and `succ` are lowered directly to arithmetic constraints.
- User-defined calls are lowered to relation atoms.
- Composition is lowered with fresh temporary result variables.
- Generic `primrec` emits base and step Horn rules.
- Recognized idioms emit closed Horn rules instead of recursive rules.
- All quantified variables are constrained with `nat`.
- Fresh names avoid collisions with user parameters such as `r`.
- User-defined function relations are prefixed with `_` to avoid collisions with
  SMT-LIB operators such as `mod`.
